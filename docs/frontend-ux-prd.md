## 4. 信息架构重组（核心）

### 4.1 分组方案

| 组 | 页面 | 说明 |
|---|---|---|
| 家 | **概览** | `dashboard`。它不是"一个功能"而是**仪表盘**：承担后端连接状态（`Dashboard.tsx:109-116`）与全局运行状态。所有成熟 Web App 的 Home 都在导航首位 |
| ① 研究 | `workflow` ★主 / `research` / `agent` / `knowledge` | |
| ② 结果 | `reports` / `evaluation` | |
| ③ 系统 | `settings` / `tutorial` | |

> **未采纳的分组**：team-lead 提示的「工作时间 / 探索 / 运维」。理由：中文语境下"工作时间"隐喻不直观，且"探索"与实际动作（跑研究、传资料、问答）不符。**「研究 / 结果 / 系统」直接对应页面动作，零解释成本。**

### 4.2 关键改名（Q1，已批准）

`workflow`「研究工作流」→ **「深度研究 ★推荐」**。

理由：它与同组的 `research`「研究规划」并列时，两个"研究"会造成严重混淆；导航的主次区分**必须靠名字表达**。"Deep Research" 已在用户词汇里，且与首页 hero、主 CTA「开始研究」一致。**只改 label 与 3 处 eyebrow，不改路由 key。**

### 4.3 三档视口的呈现方式（回答"抽屉里放几项"）

**9 项全部进抽屉，但按 3 个组标题分层，`深度研究` 置顶并带「推荐」徽标。**

抽屉是纵向富余的容器——「全量 + 分组」优于「折叠掉一半」。与现状的差别不在项数，而在：① 三个组标题 ② 视觉主次 ③ 主入口在首屏可见。

### 4.4 「下一步」引导的五种机制

1. 主次视觉层级（★推荐 + 推荐徽标）
2. 会话内页面记忆（`sessionStorage`，`App.tsx:74`）
3. 上手进度条（`localStorage['arw-onboarded']`，`Dashboard.tsx:74-88`）
4. 全局运行状态指示器（B3）
5. 命令面板（⌘K，C3）

### 4.5 首屏

概览 hero 承载后端连接状态；新访客主 CTA 变「3 步开始研究 →」。

本轮我在 A5 上界公式上连错两次（v1.2 硬编码 `11`、v1.5 推导式），两次的根因相同：**一个数在我写下它的时候，没有一条取证的是我**。

> **错误的特点不是它明显，是它长得像答案。** —— frontend-architect

那个错位的 `11` 恰好满足三条：是需求方给的（有出处感）、看着有依据（能自洽推导）、还能凑出一个整数。**三样都符合"答案"的样子，唯独不对。**

**规则（写进施工要求）**：
1. 任何进入需求的数字，必须能指到 `文件:行号`；指不到就写「推断，待核」，不许写成确定值。
2. 反证优于引用——`max_iterations default=3 / le=8` 之所以能当事实用，是因为 `schemas/graph.py:10-11` 是**约束**，不只是默认值。
3. 拿不准就**只写性质不写数值**（如 A5 只显分子、上界仅用于钳制），把数值风险关在钳制里。
4. **魔法数本身就是坏信号**：v1.2 的 `11` 被修成推导式是对的，但 v1.5 的推导式错了——**换掉魔法数不等于得到正确答案**。

### 13.2 验收标准必须能挡住"错误的实现"

- 只写「进度条不超过 95%」会放行「钉死在 95% 走完全程」——**两种表现、同一个心理机制**都读成"卡住了"。故 AC2b（不许透支）与 AC2c（不许装死）各管一头（v1.6 新增 AC2c）。
- **验收标准写错的危害大于没写**：B3-1 那次我把错误行为写进了验收标准，"错的验收会放过错的需求"。凡改验收，必须同时补**反向用例**。
- 断言要验**与数值无关的性质**（`fill ≤ 0.95`、与 steps 单调不减），不要拿建模值对后端日志做断言——图一变就假失败，且失败信息把人引向错误方向，比没有测试更糟。

### 13.3 交叉文档的一致性要靠"双侧同步"

- 两份文档各写一侧，各自看都对，但施工员会以为要管两个东西。**命名、接口这类跨文档契约，必须两边同写**。
- 只写「是同一个缝」不够：那挡住的是"误以为要管两个"，挡不住"照着再造一个"。**禁令要写在两侧同一条措辞里**。
- **变更记录不要把事件挂到被纠正的那一侧**——会让下一个人以为是自己做错了。现在 v1.6 第 ⑥ 条即按此处理（记为"双侧同步，非任一方的更正"）。

### 13.4 动手前先验证前提（本轮第二严重的错误）

`io.open(..., 'w')` 会在**求值参数前**就把文件截断为 0。我在没有备份、且 `docs/` 不在 git 管理下（`git ls-files docs/` 为空）的情况下跑了一个一次性脚本，把整份 PRD 清成空文件，最后靠逐条复核会话结论重建。

- **教训**：对**正在被消费的文档**跑任何一次性脚本前，先确认它在版本控制下或已有备份。**截断优先于异常**，错误信息不能救回已写入的内容。
- **补救动作已固化**：每次改完 PRD 都重跑一次完整性核对（行数 / 字节数 / 版本号行数 / 关键旧文本是否残留）。

### 13.5 跨层职责：不要替上游补位，也不要写"落地后删除"

- **① 跨文档「谁是权威」要逐个数定，不能默认某一侧**（v1.10 补，比下面的职责判断更靠前）。同一个数的权威来源**可以因数而异**：有的数「前端定义、后端引用」，有的数「后端定义、前端引用」——**只要逐个数写清「本数由谁定义、另一处只是引用」，就不是漂移**；**写不清的那一个，才是真漂移**。<br>⇒ 这次的洞不在"副本会漂"，而在**权威归属本身没有一把统一的尺子**：frontend 文档是阶段表的权威来源，而后端文档是同一批数据的权威来源，同一个「数」的权威来源却分在两份文档里。**不写这条，下次就会出现「副本删了，引用关系没留下」**——后人翻到那一节会以为那侧自己发明了这个数。<br>**⇒ 落法**：每处跨文档引用旁标注「来源：<文件:行号> · 定义方：<谁>」，读者一眼看出哪边是源头。
- **② 「谁的工作」问完之后还有第三种答案：谁都不属于**（v1.10 补，是第 ③ 条的 companion，否则会被用来躲问题）。答「谁都不属于」＝**真实缺口**，**不是**范围没划清。处理方式是**登记成带未来所有者的债**（写清触发条件与未来 owner），**不许静默跳过**。<br>⇒ 这不是假设：某处持久化定义的位置曾经是**空的，没有人拥有它**。而"没人拥有 = 没人更新"——下一次结构变更时**没有人会想起它**。<br>**「这不该我管」和「这目前没人管」是两件事**：前者是职责判断，后者是缺口。**只防前者，就会让后者一路滑到出事。**
- **③ 先分清一件事情归谁**：「僵尸 run 从列表消失」是**后端** AC-21 的职责（SQL 谓词），不是前端的。我一度把这条当成前端缺陷（"两边都没做导致验收落空"），实际是**AC8 把一件后端的事写进了自己的范围**。⇒ **提方案前先问"这是谁的工作"**，答不上来就说明范围没划清，别急着给方案。
- **④ 替上游补过滤 = 制造双重实现**。我提议的「过渡期前端临时承担过滤 + 注释『AC-21c 落地后删除』」被否，理由有二：① 后端一落地就是两套过滤、两套阈值；② **这类"落地后删除"的注释从来不会被删除**，但临时分支会一直活着，还会被后人当成既定设计沿用。**删除动作不发生，代码会替它存活。**
- **⑤ 更隐蔽的一层**：临时过滤会**直接废掉刚做对的那个标注**——`isStaleRun` 的全部意义是「run 留在列表里，用户能看见、能终止」。加了时间项把它过滤掉，**标注路径永远不执行**，用户只看到任务凭空消失。**检查"补位"动作时，要看它有没有把同链路上的正确路径一起掐掉。** 这条已在 v1.9 当天被实际验证过一次（跨文档权威归属的对称性缺口），见上①。

### 13.6 不变量不能只挂在"恰好在那儿"的东西上（判护栏，不是判 bug）

- **与 frontend-architect 那条判据互为镜像**：他的判兜底——「兜底分支会不会因此**永不执行**」（执行不到 = 实现过头）；本条判护栏——「**护栏被拆掉之后会不会有人知道**」（不会 = 护栏是装饰）。
- **合起来是一条**：**不变量不能只挂在一个"恰好在那儿"的东西上，无论那个东西是兜底分支还是 UI prop。它要么进类型、要么进断言、要么挂在一个会响的东西上。否则它只是长得像护栏。**
- **本轮实例**：我第一版把 P0 写成 `disabled={running}`，理由是"护栏总得有个挂点"。但 `running` 只覆盖 API 往返、不覆盖 SSE 生命周期——**护栏挂错了东西，且没有任何东西会因此报警**：拖滑块照样跳变，CI 照样绿。
- **用法**：写完任何"防手抖 / 防误用"的护栏后自问——**把它删掉，谁会知道？** 答不上来就别写它，直接去做不变量移位（让错误结果在结构上不可能），护栏只作为附带第二道。
