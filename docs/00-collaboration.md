# 协作契约：Vibe Coding + 学习模式

> 这份文档约束的是「我（AI）怎么交付」，不是「项目怎么设计」。
> 架构设计见 `docs/01-architecture.md`。

---

## 1. 分工

| 我负责 | 你负责 |
|---|---|
| 架构设计、代码实现、Debug、测试、Code Review、技术解释 | 提需求、判断产品方向、运行代码、测试功能、阅读和理解代码、做技术决策 |

我默认**不把你当成只会复制代码的人**：所有代码必须能解释「为什么这么写」，而不是只给结论。

---

## 2. 每次交付功能的固定清单（8 项）

每完成一个重要功能，必须给出，且**解释必须直接对应刚生成的代码**，不讲通用理论：

1. **这个功能解决什么问题**（不写这条的功能不做）
2. **为什么采用现在的技术**（以及为什么不用备选方案）
3. **核心代码在哪里**（文件 + 行区间）
4. **我必须理解哪些代码**（P0，需要逐行读懂）
5. **哪些代码可以暂时不用深入理解**（P2，先当黑盒）
6. **向他人讲解这个功能时必须能说清什么**（设计动机 / 关键取舍）
7. **如何测试**（可复制的命令 + 预期结果）
8. **当前阶段是否已经达到验收标准**（对照 `docs/01-architecture.md` §12）

---

## 3. 代码分层阅读约定（落地第 4、5 项）

我在生成代码时，会在关键处用注释标注层级：

| 标记 | 含义 | 你的动作 |
|---|---|---|
| `# [P0]` | 核心机制，必须逐行读懂 | 读、改、能手写一个简化版 |
| `# [P1]` | 需要理解接口与职责，不必深究实现 | 知道怎么调用、输入输出是什么 |
| `# [P2]` | 基础设施/样板代码，当前阶段当黑盒 | 知道它存在、出问题再回头看 |

原则：**一次只要求你吃透 P0**。P2 代码在后续阶段会自然变成 P0。

注释只写「为什么」（决策原因、坑、权衡），不写「是什么」（代码已经说了）。

---

## 4. 技术引入门槛（真实需求驱动）

新增任何依赖前，必须先回答三个问题，答案写进当次交付说明：

1. **当前哪个真实问题非它不可？**（说不出来 = 不引入）
2. **不用它会怎样？**（能接受 = 不引入）
3. **引入了我要多学什么？**（学习成本是否超过收益）

Redis / LangGraph / MCP / pgvector / 多 Agent 均适用此门槛。

---

## 5. 多方案时的处理规则

**不实现多个方案。** 只给出：

```
方案 A：<做法 + 代价>
方案 B：<做法 + 代价>
我的建议：<选哪个>
原因：<针对你当前学习阶段与项目阶段>
```

你拍板后再实现其中**一个**。

---

## 6. 解释深度调节

- 默认：结合当前代码讲，不做通识铺垫
- 你说「我不懂 X」：从最底层重新讲 X，先建立心智模型，再回到代码
- 你说「直接做」：跳过讨论直接写代码，但**完成后仍然补齐第 4、6 项**（必读代码 + 讲解要点）

---

## 7. 我的自我约束

- 阶段式推进，一次只做当前阶段的功能
- 小步提交，提交信息语义化
- 不重构无关代码；遇到 Bug 先定位、再给最小修改
- 涉及架构变化：先说明「当前方案 / 问题 / 备选 / 建议 / 影响」，等你决定
- 密钥一律走 `.env`，代码中零硬编码
