# 联网搜索方案说明：为什么用 Tavily，以及不依赖它的替代路线

> 适用范围：`backend/app/tools/search_provider.py`、`backend/app/tools/search_web.py`
> 相关配置：`SEARCH_PROVIDER` / `TAVILY_API_KEY` / `SEARXNG_BASE_URL` / `SEARCH_DEPTH`

---

## 1. 先分清两件事：「搜索」和「抓网页」不是一回事

项目里其实有两个不同的能力，容易被混为一谈：

| 能力 | 工具 | 解决什么问题 | 输入 |
| --- | --- | --- | --- |
| **搜索（发现）** | `search_web` → Tavily / SearXNG | 我不知道该看哪些网页，帮我找出来并排序 | 一个查询词 |
| **抓正文（读取）** | `fetch_webpage` | 我已经知道这个 URL，把正文取回来 | 一个 URL |

`fetch_webpage` 项目里**本来就有**（`app/tools/fetch_webpage.py`，带域名白名单与内网地址禁止）。
但它替代不了搜索：Agent 拿到的是「2026 年 AI Agent 岗位要求」这种问题，
它手上**没有任何 URL**，抓取工具无从下手。搜索解决的是「从 0 到 N 个候选 URL」这一步。

所以下面的讨论只针对**搜索**环节：候选 URL 从哪来、以什么形式进来。

---

## 2. 为什么默认依赖 Tavily

### 2.1 结构化返回 —— 这是最核心的一条

一次 Tavily 请求直接返回 JSON：

```json
{ "results": [ { "title": "...", "url": "...", "content": "可直接引用的正文片段", "score": 0.87 } ] }
```

`content` 是**已经抽取过正文、去过导航/广告/脚本**的纯文本片段。
它可以直接拼进 prompt，也可以直接作为证据条目存进 `evidence`。

如果自己抓搜索引擎的结果页（SERP），同样一件事要自己做完下面每一步：

1. 发起请求（要处理重定向、Cookie、压缩、编码探测）
2. 解析 HTML —— 而搜索引擎的 DOM 结构**没有公开契约**，随它们改版而变
3. 从结果页里筛出真正的自然结果，剔掉广告、知识卡片、相关搜索
4. 反爬对抗：UA/频率/验证码/JS 挑战/IP 封禁（**这一项没有终点**）
5. 再对每个 URL 抓正文、去噪、截断（又一次 1–4）

第 2 和第 4 步是**持续性成本**：不是写一次解析器就完事，而是上游一改就得修。
对一个以「研究 Agent」为核心的项目来说，把工程时间花在这上面是错配。

### 2.2 时效性

- Tavily 背后是实时索引，结果里带发布时间，可编程限定时间范围；
  研究类问题（"2026 年的岗位要求"）对时效敏感，索引陈旧会直接产出过时结论。
- 自建爬虫/自建索引的时效性取决于你的抓取频率：
  爬一遍垂直站点可能要几天，而"最近一周的行业动态"根本覆盖不到。
- 自抓 SERP 的时效性倒是没问题（就是实时查询），代价是上一节的维护成本和不稳定性。

### 2.3 调用成本 —— 自抓看似不花钱，其实更贵

| 方案 | 显性成本 | 隐性成本 |
| --- | --- | --- |
| Tavily（basic） | 1 credit/次，1000 credits/月 ≈ 1000 次 | 接近 0 |
| Tavily（advanced） | 2 credits/次，同额度约 500 次 | 接近 0 |
| 自抓 SERP | 0 元 | 代理 IP、解析维护、失败重试、被封后的停机排查 |
| 自建 SearXNG | 一台机器的成本 | 运维 + 上游引擎仍可能限流你的出口 IP |

按「一个研究 run 大约搜 3–8 次」估算，额度上限 1000 credits 能跑 **100+ 次完整研究**，
对个人/小团队验证阶段完全够用。这也是 `SEARCH_DEPTH` 默认 `basic` 的原因
（注释见 `app/core/config.py`）：先用额度换覆盖次数。

### 2.4 两个容易忽略的附带价值

- **去重与相关性排序**：商业 API 返回的是**按相关性排好序**的结果；自己拼的多个来源需要自己打分。
- **合规**：由服务商处理 robots / 站点条款问题；自己大规模抓取更容易踩到站方的反爬条款。

## 3. 不依赖第三方搜索服务的替代方案

下面 4 条路线按「自主程度」从高到低排列。**第 1 条已在代码里实现**，可直接切换。

### 方案 A：自建 SearXNG（**备选路线，本项目未采用**）

> 代码里**没有** SearXNG provider —— 它曾经实现过又被撤掉（团队范围裁定：
> 本期只做配额治理，不引入新的搜索后端）。下面保留部署方式与取舍，
> 是为了将来真要落地时不必重新调研。

SearXNG 是开源元搜索引擎：它不维护索引，而是把查询转发给你在服务端配置的上游引擎
（Google / Bing / DuckDuckGo / Brave / 百度…）并合并去重。

```bash
docker run -d -p 8080:8080 searxng/searxng
# settings.yml 里必须开启 json：
#   search:
#     formats: [html, json]
```

要实现时的工作量（约半天）：照 `TavilySearchProvider` 的样子加一个
`SearxngSearchProvider`（`app/tools/search_provider.py`）+ 在 `get_search_provider()`
加一个分支 + 一个配置项。工具层通过 `SearchProvider` 协议解耦，**业务代码零改动**。
注意要设 `billed = False` —— 自建实例不消耗 Tavily 积分，不该写配额账本。

| 维度 | 评价 |
| --- | --- |
| 结构化 | ✅ 官方 JSON，字段与 Tavily 同构（url/title/content） |
| 时效性 | ✅ 取决于你配的上游引擎 |
| 成本 | ✅ 零调用成本、无额度上限 |
| 数据合规 | ✅ 查询语句与结果不出内网 |
| 运维 | ❌ 要自己部署、监控、升级；单机吞吐有限 |
| 稳定性 | ⚠️ 上游引擎仍可能限流你的出口 IP（只是从"你"变成了"你的实例"） |

### 方案 B：换一家商业搜索 API

`OpenAICompatibleClient` 的同构思路在这里同样适用：Brave Search / Serper / Bing Search /
Google PSE 都是「一次 HTTP 请求换 JSON 结果」，照 `TavilySearchProvider` 的样子
再加一个 Provider 即可，工具层一行不用改。

| 维度 | 评价 |
| --- | --- |
| 结构化 / 时效性 / 稳定性 | ✅ 与 Tavily 同档 |
| 成本 | ⚠️ 各家额度与单价不同，按实际选型评估 |
| 自主程度 | ❌ 仍然是第三方依赖（只是换了一家） |

适合：Tavily 涨价 / 额度不够 / 需要特定区域覆盖（如百度系结果）。

### 方案 C：直接抓搜索引擎的 HTML（零成本，但最脆弱）

例如 DuckDuckGo 的 `https://html.duckduckgo.com/html/?q=...`。

| 维度 | 评价 |
| --- | --- |
| 成本 | ✅ 0 元 |
| 结构化 | ❌ 要自己写并**长期维护**解析器 |
| 稳定性 | ❌ 随时可能被反爬打断，失败模式是"静默少结果"而非报错 |
| 合规 | ⚠️ 多数引擎的服务条款禁止程序化抓取 |

**结论**：只适合做兜底/个人玩具，不适合作为项目的默认路径。
如果一定要做，建议叠在方案 A 之上（让 SearXNG 去承担解析维护），而不是自己解析。

### 方案 D：自建索引（完全自主）

自己爬一批站点 → 切块 → BM25 / 向量索引（Elasticsearch / Whoosh / pgvector）。

| 维度 | 评价 |
| --- | --- |
| 自主程度 | ✅ 最高，不依赖任何外部服务 |
| 时效性 | ❌ 取决于抓取频率，覆盖不了突发/长尾话题 |
| 成本 | ❌ 存储 + 抓取带宽 + 维护，明显高于前三种 |
| 覆盖 | ❌ 只能覆盖你爬过的站点 |

**注意**：这条路线本项目其实**已经部分具备** —— 知识库（RAG）就是"自建索引"，
只是语料由用户上传而非爬虫。对「私有文档研究」场景，直接用知识库比联网搜索更合适。

### 方案 E：只用知识库，不联网

`SEARCH_PROVIDER=stub` + 上传资料到知识库。零成本、零外部依赖、结果完全可复现；
代价是没有公开网络信息。适合内网/合规敏感环境。

## 4. 横向对比

| 方案 | 结构化 | 时效性 | 单次成本 | 运维 | 自主 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| Tavily（当前默认） | ✅ | ✅ | 1 credit | 无 | 低 | 联网研究，快速验证 |
| 自建 SearXNG（未采用） | ✅ | ✅ | 0 | 中 | 高 | 需要数据不出内网 / 高频调用 |
| 其他商业 API | ✅ | ✅ | 视厂商 | 无 | 低 | 换供应商 / 区域覆盖 |
| 自抓 SERP | ❌ | ✅ | 0 | **高** | 高 | 兜底，不推荐做默认 |
| 自建索引 | ✅ | ❌ | 存储/带宽 | 高 | 最高 | 垂直领域 / 合规内网 |
| 仅知识库 | ✅ | ❌ | 0 | 低 | 最高 | 私有文档研究 |

## 5. 切换方式与影响范围

| 改动 | 涉及文件 | 影响范围 |
| --- | --- | --- |
| 改 `SEARCH_PROVIDER` | `backend/.env.local` / `.env.production` | 仅搜索环节；Agent 循环、图节点、前端**零改动** |
| 新增一个 Provider | `app/tools/search_provider.py` + `get_search_provider()` | 同上，工具层通过 `SearchProvider` 协议解耦 |
| 配额行为 | `app/search/quota.py` | 只有 `billed = True` 的 provider 才预扣积分；自建/离线不写账本 |

关键设计：**工具层只依赖 `SearchProvider` 协议**（`search()` / `billed` / `depth`），
所以换搜索源和换 LLM 是同一种套路 —— 新增一个实现 + 改一个配置项。

## 6. 安全提醒

- `TAVILY_API_KEY` / `LLM_API_KEY` 只应存在于未入库的 `.env.*` 文件中。
  一旦泄漏，立即到对应控制台吊销重建。
- 部署环境请确认 `.env.production` 已被 `.gitignore` 覆盖（见仓库根 `.gitignore` 的 Environment 段）。
