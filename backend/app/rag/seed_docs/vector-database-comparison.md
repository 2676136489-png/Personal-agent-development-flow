# 向量数据库主流选型对比

## 为什么需要向量数据库

RAG 与语义搜索的核心是「把文本变成向量，再找最近的邻居」。向量数据库为这件事提供专门的存储与索引（HNSW、IVF 等近似最近邻算法），让百万级向量的检索保持在毫秒级。

## 主流选项

### Milvus / Zilliz
- 定位：开源分布式向量数据库，Zilliz 是其云服务版
- 优势：专为向量设计，索引类型丰富（HNSW/IVF/DISKANN），支持十亿级规模；GPU 加速成熟
- 适用：大规模生产级 RAG、多租户 SaaS、需要精细控制索引参数的团队
- 注意：运维成本偏高，小团队建议直接用 Zilliz Cloud 或 Milvus Lite（嵌入式）

### pgvector（PostgreSQL 扩展）
- 定位：在 Postgres 里加向量类型与 ivfflat/hnsw 索引
- 优势：与业务数据同库，事务、JOIN、权限体系全部复用；运维零新增组件
- 适用：向量规模千万级以内、已有 Postgres 的团队、强一致性要求高的场景
- 注意：超大规模下召回率与 QPS 不如专用库

### Qdrant
- 定位：Rust 写的专用向量引擎，API 简洁
- 优势：单节点性能强，过滤检索（payload filter）设计优秀，部署轻量
- 适用：中等规模生产环境、需要复杂元数据过滤的检索

### Weaviate
- 定位：向量数据库 + 内置模块化能力（向量化、生成式搜索）
- 优势：schema 化数据模型、GraphQL 接口、混合检索（BM25 + 向量）开箱即用
- 适用：希望少写胶水代码、快速搭建语义搜索产品的团队

### Elasticsearch / OpenSearch
- 定位：搜索引擎加向量字段（kNN）
- 优势：关键词检索最强，混合检索自然；日志生态成熟
- 适用：已是 ES 用户、需要「关键词 + 向量」混合排序的场景

### 嵌入式：Chroma / LanceDB / SQLite-VSS
- 定位：随进程运行的本地向量库
- 优势：零部署，适合桌面应用、边缘设备、开发调试
- 适用：单机小数据量（百万级以下）、原型验证、隐私敏感场景

## 选型决策要点

1. 数据规模：百万级以下优先嵌入式或 pgvector；千万级以上考虑 Milvus/Qdrant 集群
2. 团队栈：已有 Postgres/ES 就别急着引入新组件
3. 过滤需求：带大量元数据过滤选 Qdrant/pgvector
4. 运维预算：无专职运维选云服务（Zilliz Cloud / Weaviate Cloud / pgvector 托管）

## 常见误区

- 「向量数据库越大越好」：多数 RAG 应用的 chunk 量级在十万以内，嵌入式库绰绰有余
- 只看 QPS 不看召回率：ANN 索引参数（ef/search_k）需要在速度与召回之间调平
- 忽视 embedding 一致性：换 embedding 模型必须重建全部向量，模型版本要纳入数据治理
