# 多智能体编排模式与取舍

## 什么时候需要多智能体

单 Agent 循环加足工具和上下文就能解决大部分任务。考虑多智能体的信号只有两个：**上下文冲突**（不同子任务需要不同的 system prompt、工具集或知识库，塞进一个上下文互相干扰）和**并行加速**（子任务天然独立，可同时跑）。为拆而拆只会带来消息传递成本、状态同步复杂度和指数级增长的调试难度。

## 主流编排模式

- **Supervisor（主管模式）**：一个协调者把任务分派给专职 worker（检索员、分析员、写作者），收集结果并决定下一步。最常用，控制流清晰、易于加审批和预算控制；瓶颈在 supervisor 的上下文——所有结果都要过它一手。
- **Handoff（移交模式）**：Agent 之间直接移交控制权（如客服场景「售前 → 售后 → 人工」），每个 Agent 独立维护自己的上下文与工具。适合流程像流水线的场景；缺点是全局视角弱，容易在移交链上丢上下文。
- **协作群聊（round-robin）**：多个 Agent 在共享对话里轮流发言，互相评审。产出质量高（天然带对抗校验）但 token 成本数倍增长、容易收敛慢，适合离线深度分析而非在线服务。
- **流水线（pipeline）**：固定阶段依次处理，前一阶段输出作为后阶段输入。确定性最强、最好测，但没有动态调整能力——更像工作流而不是 Agent。

## 消息与状态设计

1. **传递结论不传递过程**：worker 给 supervisor 的回传要经过压缩（结论 + 关键证据引用），把完整原始过程留在 worker 自己的上下文里。回传原始输出会瞬间撑爆协调者的窗口。
2. **共享状态分层**：全局事实（任务目标、最终报告）放共享状态；中间推理放各 Agent 私有上下文。混在一起既贵又互相污染。
3. **结构化交接**：Agent 间消息用 schema 定义（如 `{findings, citations, confidence, blockers}`），下游拿到就能校验，失败早暴露。
4. **终止与预算全局化**：预算和步数上限必须挂在全局编排层，单个 worker 的局部限制挡不住「worker 之间互相触发」的循环。

## 调试与评估

多智能体的调试成本随 Agent 数量超线性增长，两个实践能显著压成本：

- **先单后多**：每个 worker 先在单 Agent 测试里跑通（给固定输入验输出），再进编排。直接端到端调试多 Agent 是新手最常见的坑。
- **轨迹回放**：把一次运行的全部消息流持久化，支持按 Agent 维度过滤查看。评估时重点看交接消息——多数多智能体故障不是某个 Agent 笨，而是交接时丢了关键上下文。

## 典型面试问题

- 什么信号出现时才应该从单 Agent 拆成多 Agent？说说你判断的依据。
- Supervisor 模式下，如何避免所有子结果撑爆协调者的上下文窗口？
- 设计一个「检索员 → 分析员 → 写作员」三角色系统：交接消息的 schema 怎么定？全局预算怎么控？
