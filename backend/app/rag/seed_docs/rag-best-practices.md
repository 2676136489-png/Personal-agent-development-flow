# RAG 检索增强实践要点

## 管线总览

一个生产级 RAG 管线包含：文档摄入（解析 → 切块 → embedding → 入库）与检索回答（查询改写 → 检索 → 重排 → 生成 → 引用核对）。每一步都有明确的工程取舍。

## 摄入阶段

### 解析
- PDF 优先选能保留页码与版式的解析器；扫描件需要 OCR，成本与准确率要提前评估
- 表格、代码块、图片说明是解析质量的三大短板，摄入后应抽检

### 切块
- chunk_size 不是越大越好：块太大稀释语义、浪费上下文；太小丢失指代与上下文
- 经验值：中文知识库 300-600 字、overlap 10%-15%
- 结构化文档（有标题层级）按结构切优于按字数硬切

### Embedding
- 中文场景选支持中文的模型（bge、text-embedding-3 系列、国产模型）
- 模型一旦选定不要频繁更换：换模型必须全量重建索引
- 无密钥的离线兜底（哈希向量）只能验证链路，没有语义泛化能力，不能用于真实检索

## 检索阶段

### 查询改写
- 用户原始问题常常不是好的检索 query：口语化、缺主语、多意图
- 常见做法：先用 LLM 把问题改写成 1-3 个检索 query，再分别检索合并去重

### 召回与重排
- 一次检索 top_k 建议 5-20，宁多勿少，把筛选交给重排
- 混合检索（向量 + BM25）在专有名词、编号、错误码类查询上显著优于纯向量
- 重排（rerank）用交叉编码器或 LLM 打分，能把 noisy chunk 压下去

## 生成阶段

- 上下文里给 chunk 编号，要求模型在结论后标注引用编号，便于前端溯源
- 明确告诉模型「只能基于给定证据回答」，减少模型自由发挥带来的幻觉
- 检索结果为零时要有明确答复策略（如实说明没找到，而不是硬答）

## 评估

- 检索质量：人工标注 50-100 条「问题 → 应命中文档」对，算命中率
- 答案质量：忠实度（答案是否被证据支撑）、相关性、完整性三个维度
- 建立回归集：每次改切块参数、换模型、调 prompt 后重跑评估集对比

## 常见故障

| 症状 | 可能原因 |
|------|---------|
| 答案说「不知道」但知识库里明明有 | 切块把关键段落切碎；查询与文档用词差异大（试试查询改写/混合检索） |
| 答案张冠李戴 | top_k 过大且没重排，噪声 chunk 混进上下文 |
| 同样的文档被重复检索 | 摄入时重复上传，未做内容去重（按内容哈希） |
| 检索全空 | embedding 模型更换后未重建索引；索引版本与存储不一致 |
