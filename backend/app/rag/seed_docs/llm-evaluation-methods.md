# 大模型应用评估方法

## 为什么评估是 LLM 工程的第一课

传统软件的正确性可以用断言表达，LLM 应用的输出是开放文本，「对不对」本身需要被定义。没有评估体系的 LLM 功能迭代等于蒙眼开车：改了 prompt、换了模型，用户反馈变好了还是变差了，全凭感觉。

## 评估的三个层次

### 1. 单元级：结构化输出
- 校验模型输出是否符合 schema（字段齐全、类型正确、枚举合法）
- 指标：一次通过率、修复后通过率、修复重试的平均次数
- 做法：固定的输入集 + Pydantic 校验，纳入 CI

### 2. 组件级：检索与工具
- 检索：命中率（应命中的文档是否进 top_k）、MRR
- 工具调用：参数正确率、工具选择准确率、无效重试率
- 做法：人工标注小规模金标数据集（50-200 条足够起步）

### 3. 端到端：答案质量
- 忠实度：答案的每个论断是否能被检索到的证据支撑（防幻觉核心指标）
- 相关性：答案是否回应了问题本身
- 完整性：问题涉及的关键方面是否都覆盖
- 做法：LLM-as-Judge（用强模型给弱模型打分）+ 定期人工抽检校准

## LLM-as-Judge 的使用纪律

- 评分标准必须写成明确的 rubric（1-5 分各长什么样），否则评委模型给分漂移
- 评委模型与被评模型不要用同一个（避免「自己批自己作业」的系统性偏好）
- 定期用人工评分校准：随机抽 10% 样本人工打分，计算人机一致率
- 位置偏好：对比两个答案时交换顺序各评一次，消除「第一个答案占优」的偏差

## 成本与延迟评估

- 记录每次调用的 prompt/completion tokens，按模型单价折算成本
- 区分「重试消耗」与「有效消耗」：修复重试占比高说明 prompt 或模型选型有问题
- p50/p95 延迟分别看：p95 差通常是流式没接好或个别上游抖动

## 评估驱动迭代的闭环

1. 建立 baseline：当前版本的指标快照
2. 每次改动（prompt/模型/参数）重跑评估集
3. 指标退化就回滚，指标持平但成本下降也算胜利
4. 线上坏案例回流到评估集，评估集随产品长大

## 常见误区

- 「感觉变好了」：没有评估集的 prompt 调整，十个里有六个是退步
- 评估集只用合成数据：合成数据分布与真实用户差很远，必须混入真实坏案例
- 一次评估定终身：模型供应商会静默升级模型，评估要定期重跑
