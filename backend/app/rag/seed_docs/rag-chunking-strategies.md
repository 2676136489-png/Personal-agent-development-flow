# RAG 切块策略：chunk size、overlap 与边界

## 为什么切块决定检索上限

检索质量的瓶颈往往不在向量模型，而在切块：块太大，一个块里混了多个主题，向量被稀释，召回排名下降，回填还浪费上下文；块太小，语义不完整，命中了也回答不了问题。切块的目标是让「一个块 = 一个自足的语义单元」，所有参数调优都是围绕这个目标的近似。

## chunk size 的经验区间

- **条目化内容**（FAQ、百科、API 文档）：按条目切块，一个条目一块，不按固定长度硬切。条目本身就是天然的语义单元。
- **叙述性长文**（报告、论文）：256~512 token 是常用区间，段落完整时优先按段落边界切，长度只做上限约束。中文场景 512 token 约对应 350~400 字，多数观点段落刚好自足。
- **代码与表格**：按函数/类/表整体切，宁可超限也不要把函数切成两半。表格切块时必须保留表头，否则单元格数据失去列语义。
- 判断标准不是拍脑袋：用评估集跑不同 size 的召回率曲线（命中率@k、MRR），拐点位置就是适合当前语料和嵌入模型的 size。不同嵌入模型对块长度的耐受度不同，换模型要重调。

## overlap 与边界处理

- **overlap 的作用**是防止关键句正好落在切点上：相邻块共享 10%~15% 的内容（如 512 块配 64 overlap）。它带来存储冗余和重复命中问题，不是越大越保险。
- **重复命中去重**：同一个句子可能出现在两个相邻块里且都命中，回填时要按来源去重，或命中后合并成连续片段再给模型。
- **结构感知切块**优先于纯长度切：按标题层级（Markdown 标题、HTML 标签）切块并继承父级标题作为元数据，检索命中后「标题链」能帮模型定位上下文。纯递归字符切分只是兜底。
- **元数据随块走**：块要携带来源、章节路径、页码/行号。引用展示、权限过滤（按部门/文档级）、按来源去重全依赖这些字段，切块时补不上的元数据，检索阶段补不了。

## 索引期与查询期的配合

- **索引期**：切块 → 嵌入 → 建索引（向量索引 + 关键词倒排）。这一步的产出是可落盘、可增量更新的数据结构，重建成本决定更新策略（全量重建 vs 增量追加）。
- **查询期**：查询改写（口语转检索词）→ 混合检索（向量 + BM25）→ 重排 → 按 token 预算组装上下文。切块粒度决定了重排的价值：块太大时重排没有精排空间，太小则要靠「检索小块、回填扩展邻块」（small-to-big）策略补全语义。
- **多粒度索引**：同一语料同时索引「细粒度块」和「章节摘要」两类粒度，事实型问题走细块，综述型问题走摘要，检索时合并两路结果。

## 典型面试问题

- chunk size 调大调小各有什么失效模式？你会怎么设计实验确定最优值？
- 为什么表格不能按固定长度切？切开后会发生什么？
- small-to-big（检索小块、回填大块）解决了什么矛盾？代价是什么？
