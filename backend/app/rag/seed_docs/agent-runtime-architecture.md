# Agent Runtime 架构设计

## Runtime 要解决什么

模型只负责「下一步做什么」的决策，真正决定系统可用性的是 runtime：状态怎么存、循环怎么停、中断后怎么恢复、失败怎么兜。很多 Agent 原型直接把逻辑写在请求处理器里，一旦涉及长任务、审批中断或多轮续跑，就要推翻重写——把 runtime 当成一个显式组件来设计，是原型到产品的分水岭。

## 核心循环

主流范式可以统一成一个状态循环：

1. 读取当前状态（目标、已有发现、上一步结果）
2. 模型决策：直接回答 / 调用工具 / 请求人工介入
3. 执行决策，把结果写回状态
4. 判断终止条件（完成 / 步数上限 / 预算上限 / 需审批），未终止则回到 1

范式差异只在决策的粒度：**ReAct** 每步都让模型边推理边行动，灵活但 token 消耗大；**Plan-and-Execute** 先产出完整计划再逐项执行，token 效率高但计划失效时需要重规划；实际系统常是混合式——先粗规划、执行中允许局部调整。

## 状态持久化与检查点

- **状态即图**：把运行状态建模成显式结构（任务队列、发现列表、证据、待审批项），而不是散落在对话历史里。状态可序列化是恢复的前提。
- **checkpointer**：每步（或每个关键节点）把状态快照落库。用途不止崩溃恢复：人工审批本质是「暂停在某个检查点，等外部事件触发续跑」；调试时可以从任意检查点分叉重放。
- **幂等续跑**：恢复时从上一个完成节点继续，工具调用要做幂等设计或记录「已执行」标记，否则同一动作可能被执行两次。
- **线程与隔离**：一次运行对应一个可寻址的线程（thread id），多任务并发的状态、锁、配额都按线程隔离。

## 中断与恢复

长任务必然会遇到三种中断，处理方式不同：

- **主动中断**（等审批/等外部数据）：状态落库、挂起进程、提供 resume 接口。恢复时把「审批结果」作为新输入注入状态。
- **被动中断**（崩溃/超时）：checkpointer 恢复到最后快照，跳过已完成步骤。
- **超限中断**（步数/预算触顶）：不是报错而是「带损收尾」——强制转入总结阶段，输出已获得的部分结论并标注哪些没完成。对用户来说，「拿到 80% 的答案 + 明确的未完成清单」远好于一个异常。

## 可观测性

Runtime 必须留三类记录：**决策日志**（每步模型选了什么、为什么）、**工具台账**（调了什么、参数、耗时、结果大小）、**成本流水**（每步 token、累计预算）。调试 Agent 90% 的时间在读这些记录——没有结构化记录的 Agent，出了问题只能靠反复重跑猜。
