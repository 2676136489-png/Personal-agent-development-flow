# Tool Calling 工程化实践

## 从「能调用」到「可依赖」

Tool Calling（Function Calling）让模型输出结构化的调用意图（函数名 + JSON 参数），由应用执行后把结果回填给模型继续推理。原型阶段一行代码就能跑通，但生产环境的核心难点在概率性：模型可能编造参数、选错工具、在不该调用时调用。工程化的目标就是把「大概率对」变成「错了也兜得住」。

## 工具 schema 设计

- **参数少而精**：可选参数超过 5 个，模型误配率明显上升。能用枚举就不要自由字符串，能用布尔就不要让模型「描述状态」。
- **描述写决策依据**：`description` 不解释「这是什么」而解释「什么时候用它、和相邻工具怎么区分」。模型选错工具，八成是两个工具的描述边界模糊。
- **必填最小化**：应用能推断或默认的参数不要让模型填（如时区、默认目录），减少一次出错机会，也省输出 token。
- **工具数量控制**：单次请求挂 30 个以上工具时选择准确率下降，按场景分组动态挂载（如「搜索类」「写入类」），或用两段式：先选类别再选具体工具。

## 执行层防护

1. **schema 校验 + 修复重试**：模型输出先过 JSON Schema 校验，失败把校验错误信息回传让模型自修，最多重试 1-2 次；仍失败降级为「向用户澄清」而不是硬跑。
2. **超时与重试分层**：工具执行设硬超时（网络类 10-30 秒），只对幂等操作自动重试，写入类操作重试前必须检查是否已生效。
3. **结果回填预算**：工具返回超长（日志、网页正文）时先截断或摘要再回填，并注明「已截断」。原始内容直接回填会把上下文窗口和成本同时打爆。
4. **不可信内容隔离**：工具返回的外部内容（网页、第三方 API）可能携带注入指令。回填时用明确分隔标记包裹，并让「引用外部内容」和「执行指令」在权限上分离。
5. **写入类工具要审批**：删数据、发消息、花钱的操作走 human-in-the-loop 确认或影子执行（先返回将执行的操作预览）。

## 死循环与成本兜底

连续工具调用的典型故障是死循环：调用失败 → 模型重试 → 同样失败。兜底三件套：

- **步数上限**：单次运行最大工具调用次数（如 15 步），触顶后强制转入总结阶段，把已有发现汇报出来。
- **重复检测**：连续 N 次相同工具 + 相同参数直接终止，重试逻辑交给应用层而不是模型。
- **预算计量**：按运行记录 token 与调用次数，超预算熔断。没有计量的 Agent 上线等于把成本放大器接到了公网上。
